# 真实任务完成链路：定向修复记录

本轮只验证“真实模型修改 → 独立测试 → 正常收尾”能否跑通，不重新计算历史矩阵成功率。
原来的 112 条真实试验保持原样。本轮每次使用独立实验 ID、全新工作区、同一模型和既有外部验收器；失败不会覆盖或自动重跑。
E02/M02 来自已公开的固定集合；另外的 D01 是单独建立的微型受控演示，不加入原评测集合。
M02 和 D01 都不能宣称未见任务泛化或真实生产事故修复。

## 已确认的故障链

1. 兼容接口的原生消息计数器不支持模型名称时，退回 UTF-8 字节上界。历史日志中约 3,000 个实际输入 token 被估成约 12,000，导致过早压缩。
2. 压缩追求软目标时丢弃刚读取的完整工具结果；摘要输入只保留首尾，函数体可能恰好处于中间，导致重复读取。
3. repoAgent 的发现没有通过 codeAgent 的声明式 context_fields 传递，实现 Agent 再次广泛探索，耗完本应留给修改和检查的预算。
4. 工具阶段结束时缺少明确的无工具总结请求，最后一轮检查后也可能不能形成有效验收判断。
5. Bash 的实际超时上限没有出现在 schema，模型提交 600/900 秒时才失败，白白消耗调用。
6. 原 M02 准备流程移除了 `examples/`，可见全量测试仍有依赖它的 MCP 用例。v4 的 Agent 重复检查这些环境故障，且多项 TODO 更新消耗了每次交接的工具预算。此任务的固定六项独立验收通过，不代表全量可见测试环境可用。

## 修复边界

- OpenAI 兼容适配器使用随包提供、校验摘要的 cl100k 估算器，同时计入消息和 schema。它是近似值，不是 DeepSeek 的精确 tokenizer 或计费数字；输出预留、安全余量及 usage 回填不变。
- 运行时不下载 tokenizer 数据；MIT 许可和来源随数据保留。其他自定义模型继续保留原有计数及保守回退。
- 最近完整工具组能容纳在硬输入上限时，优先保留它，即使软压缩目标尚未达到。任务、规则和验收标准继续保护。
- 大型仓库地图在 prompt 中提供有界投影，完整原文保存为引用；完成探索状态和发现传给实现 Agent，压缩也保留这些事实。
- 工具阶段结束后通过同一模型入口请求一次不绑定工具的总结。该请求仍检查取消、补充要求、上下文和全局预算；意外产生的工具调用补齐未执行结果，不执行副作用。
- 每轮更新剩余工具及运行预算提示，指引聚焦读取、实现、验证和汇报。未知工具只提示有效名称，不自动映射别名或扩大权限。

保持 full 默认、local 日常默认及既有权限/审批/恢复边界。
定向验证继续使用 32K 估算窗口、4096 输出、200K 运行 token、40 次请求、80 次工具、900 秒生成和独立 Docker 评分。

## D01 的任务边界

D01 只修复一个 FIFO 队列函数的数量边界及负数校验。它使用 full 流程和相同全局预算，真实模型负责探索、规划、修改与模型验收；外部评分器随后在另一个全新、无网络 Docker 容器重建可信测试。
该任务刻意很小，目的是验证完整交付链路，不用于代表跨模块任务成功率。

准备阶段实测：缺陷版本三个目标测试失败、两个基础回归通过；参考补丁五项全通过。
Agent 工作区只有六行初始实现、两个可见测试和需求说明，没有参考补丁、隐藏测试或实验报告。
允许范围仅 `src/batch_queue.py`，修改测试、无源码改动及虚假成功文本均不能通过外部评分。
