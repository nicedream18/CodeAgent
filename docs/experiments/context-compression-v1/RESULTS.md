## 为什么没有观察到压缩

只读分析使用归档中的 canonical trace 复核各次请求预算与图水位，原始结果未改写，见 [pressure.json](pressure.json)。

- 18 次运行的最大单请求输入估算为 **18,781** Token；开启组最大为 **17,279**。
- 运行时压缩水位为 **23,500**，硬输入限制为 **27,648**；图水位跨越、摘要请求和实际压缩均为 0。
- 200K 运行 Token 是所有角色、所有请求的累计预算；32K 上下文窗口约束单次请求。两者含义不同。较长任务可以多次读取/规划/验证后先耗尽累计预算，而单次上下文仍未触及压缩水位。

输入估算用于解释运行时触发条件，不能替代 API usage。即使两组总 Token、完成率或延迟不同，因实际压缩处理均未发生，也不能把差异解释为“压缩节省”或“压缩降低成功率”。本批不能证明长上下文压缩有用或无用；它暴露了当前选题与预算对压缩压力覆盖不足。

离线可控模型测试确实覆盖超水位、摘要请求计量、关闭后保留历史和输入超限停止；这些证明机制与计量行为，不计入真实模型效果。若另行做真实压力实验，应在新版本、任务、预算和实验 ID 下先确认长历史会触发压缩，再进行配对比较。本次没有为凑效果调低水位、改变任务或追加真实请求。
