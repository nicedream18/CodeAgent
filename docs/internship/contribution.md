# 展示口径与贡献说明

本轮按照维护者提供的计划，由 Codex 辅助编写实现、测试、故障分析与文档，并在本机执行检查和真实实验。
维护者确认了默认完整流程、local 后端、隔离边界、固定评测和不公开发布等约束；发现实验条件缺陷后，维护者另行授权了独立的新批次。
不要把本轮所有代码描述为本人独立手写，也不要把文档已写好等同于已经能独立解释实现。

简历可根据本人实际参与程度使用“设计并实现”“维护并完善”或“借助 AI 完成原型并独立复现”等准确表述。
以下事实可以引用对应版本和证据，禁止改写为更强的结论：

- 12 个固定任务有缺陷版失败、参考修复通过的独立验收证据。这是评分框架有效性，不能称作 Agent 解题成功率。
- baseline/full/light/auto 共用执行能力和总预算，实际结果以通过有效性核对的批次为准。
- 首批 56 次真实调用因子 Agent profile 继承缺陷标无效对照，保留完整失败记录。发现并修复这个问题是工程事实，不代表已验证多 Agent 有优势。
- 正式批次 8 份部分产物通过独立测试，但 0/56 满足“正常结束且独立验收通过”，不能简写为“完成 8 个任务”。后续 D01 与 B0/B1 另列，不能改写正式分母。
- 真实 ARM64 Docker 测试与远程 Linux CI 均已执行；远程验收准确对应 748ca5d，报告见 [Goal 3](../experiments/job-readiness-goal3/README.md)，不能归到更新后的文档提交。
- 0 次越界观察不等同于已证明任意代码安全；Docker 只隔离前台 Bash/评分，文件工具、MCP 和 hooks 仍在宿主。

面试前应本人完成以下检查，并将自己的结果另行记录：

1. 从干净 checkout 安装，独立运行离线演示和一次容器检查。
2. 不看答案，画出取消、截断和跨后端审批的执行链。
3. 从一个失败 trial 找出 run/stream/tool ID，解释终态、产物和独立评分为何可能不同。
4. 改动一个小功能，并说明需要修改的边界、失败处理和测试理由。

面试问答和工程复盘是练习材料；是否已经掌握需要通过本人操作确认，自动化测试不能替代这项验收。
