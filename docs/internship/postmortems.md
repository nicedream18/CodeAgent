# 三条执行链的工程复盘

## 1. 取消与终态发布竞争

触发：模型尚未返回首 token、正在等待审批或同步 Subagent 执行中，用户按 Ctrl+C。
若客户端直接把运行标为结束，daemon 可能还在执行；若父子任务共用同一个取消对象，独立后台任务也会被误停。

运行启动就分配 run_id 并发布 run_started。前台及同步 Subagent 共用 RunControl；显式后台任务复制必要上下文并创建独立控制器。
取消信号唤醒审批，模型 transport 关闭流；已开始的普通同步工具在现有超时内收尾，边界处检查取消，禁止启动下一项。
执行端清理完成后才发布 interrupted，checkpoint 和 trace 保留进展。

RunRecord.condition 同时保护订阅读取、状态和终态事件。结束路径在同一临界区写 status、append daemon_run_finished 并 notify；
订阅者不会先观察到终态、后丢掉最后一个事件。RLock 允许 append 内部再次取得同一条件锁。
完成竞争和重复取消由 RunControl.finish 的幂等语义解决，迟到取消不能覆盖已完成终态。

证据：M01/M05 的缺陷版与参考修复 XML，tests/test_run_cancellation.py，以及 daemon 的订阅/审批回归。
实际主实验结果必须查对应 trial，不能把参考修复通过率当成模型成功率。

取舍：普通取消不尝试撤回已完成副作用。Bash 正在执行时可能等待其超时；评测墙钟超时具有更强的专属进程/容器终止能力。

## 2. 截断响应中的工具调用保护

触发：响应先生成一个完整写入调用，后生成半个调用，最终 finish_reason=length。
SDK 可能容错补全半截 JSON；只检查 tool_calls 是否存在，会把看似完整的前半个批次执行出去。

provider 先归一化结束原因，再严格解析可取得的原始 JSON。输出上限会作废整个响应的工具调用，不依据 SDK 补全结果执行。
为每个调用补齐未执行 ToolMessage，维持消息协议；随后在同角色、同工具范围和同输出预算下缩小步骤，最多重新生成一次。
重生成前重新核对取消、补充要求、上下文与全局预算。再次截断产生明确 ModelGenerationStopped，路由、聊天、压缩及同步子任务透传。
每次真实请求有独立 stream_id，失败请求也计量、保存部分文字和终态。

证据：M02 验收；test_generation_reliability.py 覆盖完整+半截调用、严格 JSON、连续截断及取消/纠正/预算。
独立产物验收与安全停止分开。运行失败不能因为“没有产生错误写入”就计为代码任务成功。

取舍：一次重生成消耗额外请求，并可能丢弃本来正确的完整调用；优先保证批次没有被部分误执行，避免不可知副作用。

## 3. 跨执行后端的审批边界

触发：同一 Bash 命令先在 Docker 获得允许，之后切到 local，或 Docker tag 指向了其他镜像。
只按命令文本匹配，会让授权跨越不同的文件/网络/环境边界。

Bash 规则键包含规范命令、其他参数摘要、后端及固定镜像 ID。local 保留旧键以兼容已有本地规则；Docker 使用不同键空间。
镜像在运行内固定，创建容器使用 ID，不跟随 tag。单次审批保存同一执行上下文，审批后和工具开始前再次核对。
checkpoint 记录执行上下文，恢复后若不同则作废未完成决定、清除旧验证和读取快照，重新规划，不恢复旧容器或 PID。

Docker 是命令后端：每条前台命令新建容器，挂载与文件工具相同的绝对工作区路径。
默认非 root、无外网、只读 root、cap-drop ALL、禁止新增权限，限制 CPU/内存/pids；只挂载工作区和有界 tmpfs。
模型调用仍在宿主，MCP/Python hooks 和文件工具也在宿主。工作区内容并未脱敏，不能称整个 Agent 已完全沙箱化。

证据：test_execution_backend.py 的保存规则隔离、迟到批准、light/strict 恢复和真实容器测试。
macOS ARM64 的原始实验记录见 docker-arm64-2026-10-16.json；随后 Goal 3 在 748ca5d 完成远程真实容器验收，见 [Linux 报告](../experiments/job-readiness-goal3/remote/39028453552/docker/report.json)；不要将该证据归到最初 ARM64 实验版本。

取舍：每次启停容器增加延迟；没有常驻状态、不自动安装依赖、后台 Bash 明确拒绝。通过固定准备镜像换取一致性和更容易解释的边界。

## 实验中额外发现的两条边界

首批真实实验发现同步子 Agent 将运行级模型 profile 清空。模型名称虽仍相同，SDK 重试条件却不一致，导致公平性失效。
修复后默认继承父配置，显式角色配置覆盖，退出或异常恢复父配置；测试实际创建模型并经过绑定/流式请求，而不只检查初始化字段。
旧实现能让四种架构的回归同时失败。原 56 条记录另行标 invalid，用户授权的新 56 条使用独立版本，不替换旧结果。

正式批次又暴露嵌套图 `invoke` 消费 custom 事件的问题。底层 1,903 次请求与用量一致，但外层漏转发 145 条请求，另有 134 条结束事件重复记录。
原因是升级图没有向外转发流，且子 Agent 的事件副本丢失原结束事件的 trace 身份。
修复用嵌套 stream 逐步转发 custom 事件，并把 trace 标识传回生产者持有的原事件。
正常升级与生成后失败的离线回归都检查请求计数、结束唯一性和失败终态。原日志继续保留缺陷，不能事后改成“当时全部通过”。

两批真实试验没有完整成功交付，促使后续优先研究探索终止、压缩后事实保留和完成收尾，而不是继续增加工具数量。
